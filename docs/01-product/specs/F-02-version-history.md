# F-02：文档版本历史

- **状态**：已完成
- **日期**：2026-11-14
- **关联**：T-015、T-028

## 要解决什么问题

用户和 Agent 都会改文档，改错了要能回到之前的样子。版本历史在几个关键时刻给文档存一份完整正文，用户在编辑器的版本历史里、Agent 通过工具，都能看到有哪些版本，并恢复到其中一个。

每个版本都是一整篇正文，版本越多，占的空间越大。正文和文档当前的正文一样存在对象存储里，数据库只存版本的元数据。

## 做完长什么样

- [x] 以下三个时刻各生成一个版本，自动回存不生成：
  - 新建文档（「初始版本」）
  - 手动保存
  - 恢复到某个版本之前（「恢复到版本 N」，存的是恢复前的内容）
- [x] 版本正文存在 MinIO，数据库的版本表里没有正文
- [x] 编辑器的版本历史列出版本号和时间，可以恢复到其中任何一个
- [x] Agent 的 `document_version_list` 列出每个版本的版本号、标题、说明、时间和摘要
- [x] 删除文档时，它所有版本的正文对象一起删掉
- [x] 本地已有的版本迁移到 MinIO 后，都还能正常恢复

## 不做什么

- 两个版本之间的差异对比
- 在不恢复的情况下预览某个版本的全文
- 版本数量上限和自动清理

## 设计

### 交互 / 界面

不变。编辑器顶栏的时钟按钮打开版本历史，每个版本一张卡片，带「Restore」按钮。

### 技术方案

- 涉及模块：`api/`、`schemas/`
- 数据：
  - `document_version` 表存元数据：id、文档 id、版本号、标题、摘要、关键词、说明、创建人、时间。表里没有 `content` 列
  - 正文存在文档所在的桶（`user-N`）里，对象名是 `document-versions/<documentId>/<versionId>.md`。用版本 id 而不用版本号，因为版本号不保证唯一
- 接口：`GET /api/documents/{id}/versions` 只返回元数据，不带正文。前端不用正文，所以前端不用改；要重新导出 `schemas/openapi.json`
- 关键流程：
  - 存版本：先生成版本 id，写正文对象，再插入元数据。对象写失败时什么都不留；插入失败时，最多留下一个没有记录的对象
  - 恢复：从 MinIO 读出目标版本的正文，再经协同服务整篇替换（见 T-015 的实现）
  - 删除文档：先按前缀 `document-versions/<documentId>/` 删掉全部版本对象，再删记录（删除文档时都是先删存储，再删记录）
  - Agent 列版本：预览用版本表里的摘要，不读正文对象。版本再多，列一次也只查一次数据库
- 迁移：
  - 本地库：一次性任务把每个版本的正文写到 MinIO，逐个读回比对，然后执行 `ALTER TABLE document_version DROP COLUMN content`
  - 服务器还没部署过，首次部署时按新的 `mysql-schema.sql` 建表，不需要迁移

### 风险与待定问题

- 正文对象写成功、插入记录失败时，会留下一个没有记录的版本对象。概率低，删除文档时会按前缀一起删掉

## 实施拆分

1. T-028 版本正文存到 MinIO：存储读写、存版本、恢复、删除、Agent 列版本、表结构、迁移本地已有的版本

## 验证方式

- 单元测试：存版本先写对象再插记录；对象写失败时不插记录；恢复从对象读正文
- 删除文档按前缀删版本对象：在本地 MinIO 上验证
- 迁移：执行前后数版本的个数，逐个读回的正文与原来一致；迁移后数据库里没有 `content` 列
- 浏览器：新建一篇文档，手动保存，再恢复到版本 1。编辑器显示版本 1 的内容，MinIO 里有对应的版本对象；删除这篇文档后，它的版本对象都没了
- 后端测试：除 T-012 的 7 个已知失败外全部通过
