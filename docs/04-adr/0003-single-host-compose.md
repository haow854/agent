# ADR-0003：单机 Docker Compose 部署，构建产物在开发机生成

- **状态**：已采纳
- **日期**：2026-11-12
- **关联**：F-17、T-005、T-006、01-product/specs/F-17-deployment.md

## 背景

演示环境只有一台 2 核 4G 的云服务器，位于中国大陆。全部服务运行起来高峰约占 2.3 GB 内存。服务器访问 Maven 中央仓库、npm、GitHub 都慢且不稳定。

## 备选方案

### 编排：Docker Swarm

- 优点：以后扩到多台机器时不用换编排方式
- 缺点：单机下没有收益，还要多维护 overlay 网络、stack、节点约束这些概念

### 构建：在服务器上从源码构建

- 优点：服务器上只需要源码，部署结果与仓库完全对应
- 缺点：编译时额外占用约 1 GB 内存，和正在运行的服务抢资源；Maven、npm 依赖在国内下载慢

### 构建：CI 构建镜像并推送到镜像仓库

- 优点：推送代码即可部署，服务器只拉镜像
- 缺点：要配置 GitHub Actions 和镜像仓库，第一版先不做

## 决定

用一个 `docker compose` 文件在单机上运行全部服务。后端 jar 和前端 `dist/` 在开发机上构建，经 SSH 上传，服务器只用这些产物构建镜像。

## 影响

- 部署只依赖开发机和服务器之间的 SSH，不依赖服务器访问 GitHub 或各类包仓库（镜像构建时的系统软件包除外，走国内软件源）
- 本地用同一个 compose 文件就能运行与线上一致的完整环境
- 每次部署要上传约 150 MB 的后端 jar
- 线上运行的版本取决于开发机的工作区，不一定对应某个提交；改用 CI 构建后解决（T-013）
