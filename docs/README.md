# docs · Vibe Coding 知识库

这里是 docAgent 的本地 LLM Wiki：记录**要做什么、为什么这么做、做到哪了、踩过什么坑**。
代码回答 *how*，git 回答 *when*，这里回答 *what* 和 *why*。

人和 AI 都读写这些文档。每次 Vibe Coding 会话开始时，AI 先从这里拿上下文；结束时，把结论写回这里。

## 目录与归属

| 目录 | 回答的问题 | 什么时候读 | 什么时候写 |
| --- | --- | --- | --- |
| [01-product/](01-product/README.md) | 产品是什么、给谁用、有哪些功能（`F-xx`）、每个功能怎么设计 | 讨论新功能、判断要不要做某件事 | 功能新增或状态变化；较大功能动手前写 spec |
| [02-todos/](02-todos/README.md) | 现在做什么、接下来做什么、有哪些想法（`T-xxx`） | 每次会话开始 | 每次会话开始和结束 |
| [03-journal/](03-journal/README.md) | 每次会话做了什么、留下了什么 | 接手上次没做完的事 | 每次会话结束 |
| [04-adr/](04-adr/README.md) | 为什么选 A 不选 B（`ADR-xxxx`） | 想改架构或推翻旧方案前 | 做出有取舍的决定时 |
| [05-postmortems/](05-postmortems/README.md) | 出过什么问题、根因是什么、以后怎么防 | 做同类改动前 | 线上故障、严重 bug、AI 改坏东西导致返工之后 |

编号前缀就是阅读顺序：先看产品，再看待办，需要时再翻日志、决策和复盘。每个目录的 README 是该目录的索引和规则。

## 一次 Vibe Coding 会话的流程

```text
开工                          进行中                               收工
 │                              │                                   │
 ├─ 读 02-todos 的「进行中」    ├─ 新想法 → 02-todos 收件箱          ├─ 更新 02-todos 状态
 ├─ 读相关 spec / ADR / 复盘    ├─ 功能较大 → 先写 spec 再写码       ├─ 更新 01-product 功能地图
 └─ 明确本次目标                ├─ 做出取舍 → 04-adr 新增 ADR        ├─ 03-journal 新增一篇
                                └─ 出了事故 → 05-postmortems 复盘    └─ 复盘的教训写回 AGENTS.md
```

### 什么时候必须先写 spec

满足任意一条，就先在 `01-product/specs/` 写设计、确认后再动代码：

- 跨两个以上模块（如 `api/` + `web/`，或 `api/` + `collab-server/`）
- 改动接口契约（`schemas/`）或数据库表结构（`api/mysql-schema.sql`）
- 预计一次会话做不完
- 说不清「做完长什么样」

小改动（修 bug、调样式、补测试）不需要 spec，在待办里记一行即可。

### 什么时候写 ADR

做了一个**三个月后可能有人问「当时为什么这样」**的决定：

- 技术选型（引入或替换某个库、中间件）
- 架构约定（某类逻辑放在哪一层、数据存在哪）
- 有意不做某件事（明确放弃一个方向）
- 推翻之前的决定（新 ADR 标注「取代 ADR-xxxx」，旧的不删）

### 什么时候写复盘

- 部署或线上出了故障
- bug 花了超过一次会话才定位
- AI 的改动把别的地方改坏了，或者方向错了导致返工

复盘的目的是**不再犯第二次**：每篇复盘至少产出一条行动项，要么是待办，要么是写进 `AGENTS.md` 的约定。

## 编号与命名

| 类型 | 格式 | 示例 | 位置 |
| --- | --- | --- | --- |
| 功能 | `F-xx` | F-07 | 01-product/features.md |
| 功能设计 | `F-xx-<slug>.md` | F-18-doc-outline.md | 01-product/specs/ |
| 待办 | `T-xxx` | T-012 | 02-todos/backlog.md |
| 日志 | `YYYY-MM-DD-<slug>.md` | 2026-11-11-monorepo-and-docs.md | 03-journal/ |
| 决策 | `NNNN-<slug>.md` | 0003-xxx.md | 04-adr/ |
| 复盘 | `YYYY-MM-DD-<slug>.md` | 2026-11-20-deploy-oom.md | 05-postmortems/ |

编号只增不复用，下一个可用编号写在对应目录里。文档之间用编号互相引用，例如「T-012 实现大纲面板（F-18，见 01-product/specs/F-18-doc-outline.md）」。

## 维护原则

- **短比全重要**：每份文档保持一分钟内能扫完。写不下就拆，或者删旧的。
- **状态要真实**：没验证过的不标「已完成」。
- **只追加历史**：日志、已采纳的 ADR、复盘不改写，只追加。
- **不重复代码**：接口字段、类结构看代码就行，这里只写代码里看不出来的东西。
